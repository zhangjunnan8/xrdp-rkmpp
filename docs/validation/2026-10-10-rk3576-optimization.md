# RK3576 桌面流畅度优化验收

日期：2026-10-10。对象：KICKPI K7 / RK3576 / Ubuntu 24.04 arm64 / 6.1.75 厂商内核。
范围：`feat/rk3576-direct-mpp` 分支，直接对接 MPP，不引入通用兼容层。

## 部署和来源

- XRDP 0.10.6.1 与 xorgxrdp 0.10.5 官方归档均核对 SHA-256，原生编译。
- 最终两份二进制构建提交：`071e67e75c73c6d02e0b59de4e14510f48b4d205`。
- 安装：`/opt/xrdp-rk3576-lab/<构建SHA>` 与 `/opt/xrdp-rk3576-xorg/<构建SHA>`；不覆盖系统模块。
- 服务：`xrdp-rk3576-lab`、`xrdp-rk3576-lab-sesman`，端口 3391，桌面从 `:50` 开始。
- 最终日常设置：QP 18、DIRECT=1、PIPELINE=1、STRICT=0；硬件失败时明确记录并回退 x264；开机启动已启用。
- `3390 / :30` 的既有桌面保持原状；测试使用另一独立实例。
- 自动测试独立使用 独立客户端的私有 Xvfb `:97` 和私有 FreeRDP 2.11.5（FFmpeg H.264 解码），不把客户端解码负载加在 RK3576 上。
- 后续提交仅补充测试工具、部署工具、说明和验收数据；不改变上述两份已验收二进制的编码/转换实现。

## 实现

1. xorgxrdp 的 BGRA → BT.709 全范围 NV12 改为 NEON，保持上游整数系数、逐像素舍入与 2×2 色度平均结果。
2. MPP 持久化的 DMA 输入直接接收变化区域，省去正常路径的 CPU 影子图重复复制；缓存同步保留。失败时先安全恢复完整画面，再进入软件 IDR 恢复。
3. 输入复制完成后允许 Xorg 抓取下一帧，与 MPP 编码重叠。仅接管满足严格边界检查的单帧 AVC420 批次，真实客户端 ACK 与原有在途帧数限制不变。复杂批次沿用上游调度。
4. 增加真实窗口运动和变色动画、独立 LAN 客户端、分辨率轮换与分阶段 profiler，检查实际编码而不是动画绘制计数。
5. 部署时清理本测试命名空间中可能残留的 chansrv，并拒绝在仍有测试客户端连接时更新。避免把旧 `:50` 的后台动画误当成另一个新桌面的负载。

## 正确性检查

| 检查 | 结果 |
|---|---|
| NEON 与上游原函数比较 | 原生和 UBSan 各 605 组，包含所有 16,777,216 种 RGB、非整齐宽度、步长与写入哨兵；逐字节相等 |
| 单帧命令解析 | 100,049 项边界、保护页与变异检查，UBSan 通过 |
| H.264 独立 FFmpeg 解码 | 9 组：小尺寸、318×242、1080p、1440p、4K、局部/全帧、多 QP；帧数、颜色范围、无 B 帧、空闲后 IDR 与画质通过 |
| 输入重用 | 上述解码测试在 input-ready 回调内立刻毒化源内存，结果与原来一致 |
| 生命周期及回退 | 原生和 UBSan 各 2,552 项，80 次创建/改尺寸/销毁；fd 11→11，原生 RSS 5,284→5,284 KiB，UBSan 6,952→6,956 KiB |
| 丢失输出后恢复 | 注入输出容量失败，同时毒化已归还源内存；软件下一帧重建 IDR，独立解码 PSNR 53.861 dB |
| 实际 RDP 设备不可用 | 仅对 lab unit 使用临时 InaccessiblePaths 隐藏 `/dev/mpp_service`；明确切换 x264，客户端两次截图内容不同，连接存活；随后移除故障设置并恢复硬编码 |

该厂商内核的 39 位地址空间不能运行本机 ASan；未把 ASan 记为通过。UBSan、保护页、写入哨兵和独立解码承担这里实际执行的检查。

最终 NEON 1440p 全帧转换单测：标量 24.099 ms，NEON 5.141 ms，约 4.69 倍；该微基准与桌面局部损伤的每帧耗时不同。
QP 18 的解码 PSNR 为 54.935–57.392 dB，和优化前同一合成数据一致。没有通过降低画质提高帧率。

## 连续实际桌面检查

最终同条件开关对照使用相同的 XRDP 二进制、QP 18、2560×1440、16 ms 帧间隔和 独立 FFmpeg 客户端，均为新建的单屏会话。基线关闭 DIRECT/PIPELINE 并使用原标量 Xorg 模块；优化组开启两项设置并使用 NEON 模块。两组均运行 60 秒，硬编码证据检查通过。测试工具提交为 `7994e66`，原始目录为 `bench-final-baseline-1440` 与 `bench-final-optimized-1440`。

| 负载 | 基线 FPS | 优化 FPS | 提升 | 抓屏均值：基线→优化 | 编码均值：基线→优化 |
|---|---:|---:|---:|---|---|
| 窗口拖动 | 19.834 | 35.889 | 81% | 18.908→3.955 ms | 24.375→19.224 ms |
| 快速变色 | 25.111 | 49.445 | 97% | 11.750→2.483 ms | 21.504→17.714 ms |
| 拖动加变色 | 20.278 | 36.500 | 80% | 17.042→3.695 ms | 24.599→19.519 ms |

优化组运行期无错误、无回退、trace 无丢失；两组最大未确认帧数都为 2。编码与抓屏现在可以重叠，表中的阶段时间不能直接相加推算实际 FPS。

同一连接每种尺寸运行 60 秒，依次 1440p → 1080p → 4K → 1080p → 1440p。
共 300 秒动画，五段均通过；每段三个 20 秒阶段，报告时统一排除每阶段前 2 秒。

| 尺寸与顺序 | 拖动 FPS | 变色 FPS | 混合 FPS |
|---|---:|---:|---:|
| 1440p 首次 | 36.778 | 48.889 | 36.222 |
| 1080p 首次 | 36.166 | 30.223 | 40.944 |
| 4K | 22.111 | 26.722 | 21.056 |
| 1080p 回切 | 47.278 | 33.000 | 43.000 |
| 1440p 回切 | 34.889 | 44.722 | 36.444 |

实际测量的未确认帧最多为 2；运行期没有编码失败、软件回退或 trace 丢失。XRDP fd 每段均回到 45。进程 RSS 在 4K 扩容后保留约 65 MiB 的高水位，后续同尺寸段稳定，没有把“缩回后 RSS 未立即下降”描述成完全归还内存，也不把五分钟检查视为无限期无泄漏保证。

1080p 两次结果存在波动，说明桌面合成、客户端呈现和定时调度仍会影响实际帧率；4K 也未达到 60 FPS。此处为服务端实际编码速率，不是显示器呈现 FPS，也不是鼠标到屏幕的端到端延迟。

## 测量与交付限制

- 动画使用真实 X11 窗口移动、像素变化和表格小字；覆盖合成、抓屏、转换、编码、传输和解码，不替代文件管理器磁盘访问或真实用户输入延迟检查。
- MPP 使用 RKVENC 编码单元，Mali GPU 在采样中仍为 0%；这不代表没有硬编码。桌面绘制与部分复制仍消耗 CPU。
- 不启用 RGA、零拷贝、Glamor、AVC444 或广泛多屏优化；这次保持了现有 AVC420 链路的颜色和故障边界。
- 没有更改 CPU/GPU 频率、电压或系统驱动，没有关闭用户现有桌面特效。
- 验收数据是合成桌面；原始截图、日志、码流、凭据不提交仓库。可复现入口见 [无人值守说明](../unattended-benchmark.md)。
- 3391 是独立新桌面；3390 中的现有应用窗口不会自动搬过去。后续若有人已在 3391 办公，更新它也会影响该桌面，应另建测试端口或安排切换。
