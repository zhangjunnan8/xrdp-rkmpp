# Default 1080p connection / 默认 1080p 连接验证

Date: 2026-10-13. This change updates the RDP profile and documentation only. The running optimized encoder remains the native build from public source `754eddb5ec46d5848b880e7e7295deb5318e0ae9`; no encoder change or service restart was required.

## Connection defaults

The supplied `RK3576-optimized.rdp` now requests one 1920×1080 desktop on TCP 3389. It starts windowed, disables automatic dynamic-resolution changes, and enables client-side smart sizing. Resizing the local window therefore need not increase the remote pixel count. Users may change the profile dimensions/client display settings and reconnect, or explicitly enable dynamic resolution.

This is a connection-profile default, not a server-enforced size or codec scaling limit. Clients connecting with their own settings may request other dimensions. Property definitions were checked against [Microsoft's RDP documentation](https://learn.microsoft.com/en-us/azure/virtual-desktop/rdp-properties#display-settings).

## Actual check

On the existing headless RK3576 / vendor Ubuntu 24.04 board, a separate Linux FreeRDP 2.11.5 client loaded the updated profile with site address/account substituted locally. No command-line width/height or dynamic-resolution override was supplied. The client used AVC420 and the server certificate fingerprint retrieved over verified SSH.

- Xorg `xrandr --current`: **current 1920 x 1080**, output `rdp0` at 1920×1080.
- Server log: MPP opened **1920×1080**, completed its first hardware frame and subsequently encoded desktop updates without x264 fallback.
- MPP's coded buffer height was 1088 due to hardware alignment; the displayed desktop remained 1080 pixels high.
- The temporary client/Xvfb output was removed and the owned test desktop ended. The listener and session manager remained active and enabled, with no service restart.
- Public-tree hygiene, Python syntax, Markdown links and whitespace checks passed. The site cleanup PowerShell script received syntax validation only, not execution.

The controller's initial result-printing step encountered a Python string/bytes mismatch after launching the client. The client completed its run, and the negotiated dimensions and hardware completion were verified independently from Xorg and the new server log entries. This was a test-reporting error, not an encoding failure.

Windows mstsc rendering was not retested in this round. The earlier single-instance [headless deployment validation](2026-10-13-single-instance.md) remains applicable; no new FPS or latency claim is made.
