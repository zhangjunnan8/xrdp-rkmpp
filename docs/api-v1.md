# 插件 API v1

> Historical generic prototype / 历史通用原型：不用于当前 RK3576 直接硬编码路径。当前实现见 [RK3576 integration](../rk3576/README.md)。

这是 0.1 开发版接口。ABI 标识为 `CB_ABI_V1`，当前值 `0x00010000`。后续破坏性变更必须升级 ABI；这里的 v1 不表示已经完成多厂商验证。

## 组件

- `include/codecbridge/backend.h`：插件 SDK，只依赖标准整数类型，不包含厂商头文件。
- `include/codecbridge/codecbridge.h`：应用使用的加载、探测和编码会话 API。
- `libcodecbridge.so`：核心加载器、输入校验、状态和资源生命周期管理。
- `cb_backend_x264.so`：首个独立编码插件，通过系统 x264 软件编码。
- `cb-encode`：探测插件和生成测试码流的命令行工具。

插件导出 `cb_backend_query(uint32_t requested_abi)`，返回完整的 `cb_backend_v1` 函数表。不支持所请求版本时返回 NULL。加载器拒绝 ABI 不符、结构过小、缺少入口或缺少必需函数的插件。插件与宿主必须使用相同机器架构和兼容的 C ABI。

只加载来自受信任构建的插件：共享库直接在宿主进程运行，ABI 检查不构成安全沙箱。插件要为每个编码会话持有独立状态；v1 调用由应用外部串行化。

## 能力探测和创建

`cb_plugin_probe()` 返回 codec、输入格式、内存和 profile 的支持位，以及尺寸范围、对齐、可在途帧数和硬件标记。设备不可访问、缺少驱动和配置不支持要返回错误，不能用静态品牌判断替代探测。探测成功后 `create` 仍可能失败。

当前核心和软件插件只支持：

| 属性 | v1 已实现范围 |
|---|---|
| 编码输出 | H.264 Baseline；Annex B；每包一个完整 access unit |
| 输入 | 完整 NV12 图像，CPU 可访问的两个平面 |
| 颜色 | BT.601 / BT.709；limited / full |
| 尺寸 | 核心要求偶数；x264 后端当前报告 16..8192，每方向按 2 对齐 |
| 码率控制 | 固定 QP 1..51；默认 23 |
| x264 参数 | ultrafast、zerolatency、无 B 帧、默认 2 个 slice 线程 |
| 排队 | x264 插件最多 1 个尚未释放的输出包，超过时产生背压 |
| 尺寸或颜色变化 | 销毁旧会话，以新 generation 创建新会话 |

`cb_config_default()` 初始化所有必需字段。帧和包等调用方分配的结构需要清零并设置 `struct_size = sizeof(...)`。大于当前版本的结构尾部不会由核心解释。不能把未来支持的格式填入字段后期待静默转换。

软件插件不接受设备路径，也不支持 DMA-BUF。后续硬件插件可以在现有 CPU 输入契约下先复制到驱动缓冲区；新增零复制内存类型时再明确其生命周期扩展。

## 帧、时间戳和码流

`cb_frame` 包含各平面地址、容量和步长。核心按有效行计算所需容量，拒绝缺失平面、步长不足、容量不足、错误尺寸和错误 generation。输入必须包含完整有效图像，局部更新的合成由未来 XRDP 适配层负责。

`frame_id` 用于应用关联输入和输出；`pts_us` 是应用提供的非负微秒时间戳，在同一会话中必须严格递增。只有成功接受输入才推进上一个时间戳。`generation` 是应用指定的会话/配置代次，新配置必须由应用分配新值。

x264 内部使用配置帧率对应的 CFR 时基及顺序帧号，从而避免 VFR 模式额外缓存一帧；原始 `pts_us`、`frame_id` 和 `generation` 原样返回到 `cb_packet`。裸 H.264 文件本身不保存这些应用时间戳。帧率参数是名义编码时基，命令行工具默认不按该帧率等待。

第一帧以及请求后的下一帧为 IDR，前面重复 SPS/PPS；每帧包含 AUD。输入已经接受后再发生编码失败会使会话失效，调用方需销毁重建，不能将该会话当作未消耗过输入继续工作。

## 生命周期与背压

正常顺序：

```text
plugin_load → plugin_probe → encoder_create
  → [submit → receive → packet_release] × N
  → drain → receive 到 EOF → encoder_destroy → plugin_unload
```

`submit` 与 `receive` 是分离的调用，以便后续异步后端接入。成功提交后，插件已经复制或完成使用输入；调用方可以立即复用输入内存。x264 插件在 `submit` 中同步编码，`receive` 返回已经生成的包。

未取出/释放的包占满 x264 队列时，再次 `submit` 返回 `CB_AGAIN`，该次输入未被接受。`receive` 成功后，包由插件持有、应用借用；必须调用 `cb_packet_release()`，不能自行 `free()`。持有包期间核心拒绝再次收取、提交、排空和销毁。释放后的包不能继续读取。

输出不可用时返回 `CB_AGAIN`。硬件后端可以在 `receive(timeout_ms)` 中等待至指定上限，然后返回 `CB_ERR_TIMEOUT`；没有工作在途时可立即返回 `CB_AGAIN`。这些超时是合作式约定，不能中断卡住的驱动调用或隔离进程内插件崩溃。

`drain` 成功后不再接受输入。已排队的输出仍可收取和释放，最终返回 `CB_EOF`。允许直接销毁没有借出包的会话以取消未收取输出。仍有存活会话时卸载插件返回 `CB_ERR_BUSY`。

## 错误和恢复

正数状态 `CB_AGAIN` / `CB_EOF` 与负数错误分开。无效参数、格式不支持、资源忙和超时不自动破坏会话。`CB_ERR_DEVICE` 或 `CB_ERR_BACKEND` 使会话进入失败状态；之后仅允许释放已借出的包并销毁。

阶段 1 使用显式插件路径，不自动选择另一个编码器。未来自动回退应在更高一层重建会话和配置代次，并输出新码流头和 IDR；禁止把两台编码器的参考帧状态拼接起来。

## 验证范围

契约测试使用明确标为 `test-fixture-not-a-codec` 的故障注入插件，覆盖 ABI 拒绝、错误能力、超时、设备故障、错误代次和资源所有权。这些测试插件不会作为产品编码器安装。

x264 生命周期测试检查重复创建销毁、未接收输出的销毁、背压、强制 IDR 及码流头。独立 FFmpeg round-trip 测试验证实际帧数、尺寸、颜色标签、无 B 帧，以及解码图像与原 NV12 图像的 PSNR。测试结果不等同于真实 RDP 会话验证。
